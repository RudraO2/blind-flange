# Epic 5 Context: Real work, real deliverable

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

The workbench does the work instead of talking about it: the agent runs end to end on a
scanned inspection report, helper agents spawn and are visibly working, a coding task
executes and is verified inside the sandbox, and the run ends in a real `.docx` — titleblock,
reference number, cited clauses, signature block, and a provenance footer with a content hash
— that opens clean in both LibreOffice and Word. This is the P0 checklist item that proves the
product produces work product, not chat, and it is the largest remaining lever on the
four-day schedule because most of the surface code already ships in the harness.

## Stories

- Story 5.1: The agent turns a scanned report into key findings
- Story 5.2: Helper agents are visible while they work
- Story 5.3: A coding task runs and is verified in the sandbox
- Story 5.4: The approval note comes out as a signed .docx
- Story 5.5: The fan-out gauge feels alive while agents work — DEFERRED 28 Aug 2026 (polish
  pass, out of Phase 0 scope; revisit only once 5.1–5.4 work end to end)

## Requirements & Constraints

- The agentic run must use a real harness agent loop with at least one real tool call; findings
  must carry the provenance already established for ingestion (page/box/confidence).
- The full turn flow (every tool call and result) must be reconstructable from the session log.
- A multi-step plan must be shown as it actually advances — driven by real tool calls, never by
  a timer or a canned animation (this project's NFR8: no animation without a real event behind
  it).
- A sub-agent fan-out indicator must reflect real spawn/settle events, return to a resting state
  when the run completes, and must not idle-animate against a zero count.
- A coding task must execute inside the harness sandbox, and both the run and its result
  (including failure) must be visible in the UI rather than swallowed.
- The sandbox's shell tool must be proven sealed against outbound network calls the same way the
  existing network canary is proven: attempted egress from inside the shell must be denied and
  counted by the egress monitor. This closes a real gap — the shipped egress denylist matches by
  tool name and does not yet include the shell tool.
- The produced `.docx` must contain: titleblock, reference number, cited clauses (traceable back
  to findings and their provenance), signature block, and a provenance footer with a content
  hash. It must be generated by a real tool registered through `defineTool`, never
  pre-authored/templated-and-faked.
- The produced file must surface through the shipped produced-files UI (Open / Show-in-folder)
  and its path must also be reachable from the response text, so a harness change to card
  handling degrades the row rather than losing the file entirely.
- Only Apache-2.0 / MIT / BSD-2-Clause / BSD-3-Clause dependencies are permitted anywhere in this
  epic's build (weights, dependencies, harness extensions).

## Technical Decisions

- **Most of this epic's UI already ships and must not be rebuilt.** The panels are mounted and
  active in the harness's web profile; only the model-facing *tools* that drive them are
  disabled. Enabling a tool row via a `cordis.patch.yml` row is in scope; hand-rolling a
  duplicate component beside a shipped one is the mistake this project already made once
  (Story 1.4's task-type picker) and must not repeat.
  - Story 5.1: `goal` / `ui-goal` (GoalBar) already active → enable `tool-goal`
    (`create_goal`, `get_goal`, `update_goal`).
  - Story 5.2: `jobs` (`ctx.jobs`), `ui-jobs`, `ui-subagent`, `subagent-spawn-in-process`,
    `subagent-fork-in-process` already active → enable `tool-jobs`, `tool-subagent`,
    `tool-subagent-control`.
  - Story 5.3: `sandbox` (local), `sandbox-policy`, `pwsh-sandbox` already active → enable
    `tool-pwsh` (and `tool-fs` only if the task needs file access).
  - Story 5.4: `ui-deliverables` already active at `conversation.chat.turnTail` → no tool to
    enable; this story is pure server-side tool work.
- **Windows executor is `pwsh-sandbox`, not `dsh-bash-sandbox`.** The bash sandbox row carries a
  `disabled` expression true on win32 and never loads on the build machine.
- **`dsh-sandbox-local`'s Windows backend confines filesystem writes only** (ACL restricted
  token, `workspaceWriteSid`/`tempWriteSid`) — it applies **no network confinement**. The
  existing egress waterfall (`plugins/dsh-client-ui-base/lib/index.js`) denies by tool *name*
  and today only covers the two shipped web tools; a `pwsh` call is a different name and passes
  through unless Story 5.3 extends the seal.
- **`ui-deliverables` recognises a produced file by render intent, not tool name** — a `diff`
  card, or a `generic` card with `kind: edit` reading `locations[].path`. Returning that shape
  from the `.docx` tool gets the clickable deliverable row for free; writing the document
  content (titleblock, reference number, citations, signature block, provenance hash) is still
  fully this project's own work — nothing in the harness produces it.
- The harness is pinned at `0.1.1-rc.2`; build against its exposed contracts only. Enabling a
  shipped, disabled tool row is safe. Reaching into these packages' internals is not — any story
  depending on their behaviour must degrade gracefully, not vanish, if that behaviour changes.
- Page rendering / OCR provenance (page, bounding box, confidence) established in Epic 4 via
  RapidOCR + `pypdfium2` feeds Story 5.1's findings and Story 5.4's cited-clause traceability;
  `PyMuPDF` remains prohibited (AGPL-3.0) anywhere this epic touches document rendering.

## UX & Interaction Patterns

- Plan/step progress renders in the shipped GoalBar (`conversation.input.dock` and
  `conversation.chat.node`), not a custom plan panel. If the GoalBar genuinely cannot carry the
  plan, the documented fallback is naming steps in response text — not reimplementing the panel.
- Sub-agent activity renders via the shipped `ui-jobs` (session header actions) and
  `ui-subagent` (session header lineage, composer) surfaces, not a new fan-out gauge.
- Produced files render via the shipped produced-files row (Open / Show-in-folder actions) at
  `conversation.chat.turnTail`.
- Restraint over decoration still applies project-wide: no animation plays without a real event
  behind it, and no idle/looping motion plays against a resting or zero state.

## Cross-Story Dependencies

- Story 5.4's cited clauses depend on findings and their provenance produced by Story 5.1 (and,
  upstream, by Epic 4's OCR/crop pipeline).
- Story 5.3 depends on Epic 2's network-egress canary/monitor pattern, which it must extend
  (not replace) to cover the shell tool — a second canary proving denial of egress attempted
  through `pwsh`.
- Story 5.5 is deferred and depends on Stories 5.1–5.4 being demonstrably working end to end
  before it is picked up; it enhances the same `ui-subagent` control Story 5.2 enables rather
  than introducing a new component.
- All four active stories share the same enable-don't-rebuild constraint: each must check the
  named shipped surface against its acceptance criteria before writing any UI code.
